# 2026-07 月度报告

> [English](../../monthly/2026-07.md) | **简体中文**

> **覆盖范围：** 2026-07 首次公开的工作

## 本月概览

2026 年 7 月从数量上看没 6 月那么猛，但结构更集中。这个月主要围着一个问题转：如果 agent 的输出最后要对外部机构、物理过程、或者专家 workflow 负责，而不是只对 benchmark 自己那套打分规矩负责，那 evaluation 该怎么做？最清楚的例子就是桥梁检测排序、物理/天体物理文献综述与项目计划书、结构可靠度分析，以及在固定算力预算下改世界模型。

第二条主线是，skill 和 trajectory 这两边都明显变“更不客气”了。不再只是问“平均来看 skill 有没有帮助”，而是开始追问：agent 说自己用了某个 skill，这件事到底有没有因果作用？skill 生命周期里哪些环节本身就是安全边界？长时程运行中间那些步骤，能不能真的把翻车点揪出来？

## 这个月到底变了什么

### [Scientific Agent Benchmarks](../../topics/scientific_agents.md)

7 月 scientific benchmark 的一个很鲜明特点，是它更认真地把分数绑到外部现实上。[Cognitive Agents for Bridge Inspection Prioritization](../../works/cognitive-agents-for-bridge-inspection-prioritizat.md) 很适合当锚点，因为它不是拿手工标签关起门来打分，而是直接对照六年 NBI 年度快照里桥梁后续真实劣化情况来评，再让持证桥梁检测工程师盲评 agent 写出来的理由。那两篇物理/天体物理/宇宙学的文献综述和项目计划书工作也是同一路子：强行让 AI 输出去对专家工作流负责，而不是只对一套 synthetic benchmark protocol 负责，同时还把编造、元数据错配、评审能否分辨作者、以及 LLM judge 偏向都摊开来量。

[Automating Structural Reliability Analysis with a Multi-Agent Large Language Model Framework](../../works/automating-structural-reliability-analysis-with-a.md)、[LQCDMaster](../../works/lqcdmaster.md)、[FukuyamaBench](../../works/fukuyamabench.md)、[Imaging-101](../../works/imaging-101.md)、[MDArena](../../works/mdarena.md)、[OntoLearner](../../works/ontolearner.md)、[StructureClaw](../../works/structureclaw.md) 把学科面铺得更开，但更有意思的新增其实是 [AutoWorldModel-Bench](../../works/autoworldmodel-bench.md)。它放在 scientific benchmarking 里，是因为它评的是固定预算下的迭代改模能力；但它也顺手把仓库的新 scope 说明白了：evaluation 不只是给一个完成品 agent 判分，还可以把“下一轮模型更新本身”做成任务、做成受控回路。

### [Skill Hierarchy](../../topics/skill_hierarchy.md)

7 月的 skill 文献，不再把“agent 说自己用了 skill”当成可直接相信的事。[BACKROOMBench](../../works/backroombench.md) 把这个问题说得最直白：agent 可以在 explanation 里声称自己用了某个 skill，但真正有意义的是，干预实验能不能证明这个 skill 对答案真的有因果作用。[SkillCoach](../../works/skillcoach.md) 则把这种压力延伸到过程评估里：skill selection、following、composition、reflection 分开打分，而且 rubric 还会从真实 rollout 里长出来。

这个月另一条明显变化，是 skill repository 开始被当成攻击面和运维系统来看。[SkillSec-Eval](../../works/skillsec-eval.md) 直接把生命周期拆成五道 trust boundary；[LabRobFail](../../works/labrobfail.md) 则在化学 self-driving lab 里按 control、physics、semantic 三层去打 failure；[SciExplore](../../works/sciexplore.md)、[SLBench](../../works/slbench.md)、[UniClawBench](../../works/uniclawbench.md) 也都在往同一个方向收束：一旦 skill 成了可复用基础设施，evaluation 就不能只问“有用没用”，还得问它会在哪层坏、怎么被操纵、以及 agent 自己知不知道它当前用的是哪一层能力。

### [Trajectory Evaluation](../../topics/trajectory_evaluation.md)

7 月的 trajectory evaluation 更像是在做“运行过程仪表化”。[AgentLens](../../works/agentlens.md) 不是简单说“我们把步骤记下来了”，而是把 formal verification、LLM trajectory review 和 side-by-side comparison 真并在一起。[Long-Horizon-Terminal-Bench](../../works/long-horizon-terminal-bench.md) 则从另一个方向解决问题：它把长 terminal run 切成 graded subtasks，给出 dense intermediate credit，于是 evaluator 看得见，开发者也知道该从哪儿下手。[OSReward](../../works/osreward.md) 和 [Who&When Pro](../../works/who-and-when-pro.md) 也都在继续追这个“中间责任到底落在哪儿”的问题。

合起来看，7 月的 trajectory work 重点已经不是“轨迹很长很复杂”，而是“能不能把黑箱 run 变成一串可 review、可 blame、可 reward、可 intervention 的中间事件”。

## 值得展开的 Topic

7 月确实还是 [Scientific Agent Benchmarks](../../topics/scientific_agents.md)、[Skill Hierarchy](../../topics/skill_hierarchy.md)、[Trajectory Evaluation](../../topics/trajectory_evaluation.md) 最活跃，但更重要的是这三页开始互相咬合：benchmark 越来越依赖专家 workflow 和真实结果，skill 文献开始讲因果和安全边界，trajectory 这边则在补足把前两者连起来的 instrumentation。
