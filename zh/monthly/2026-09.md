# 2026-09 月度报告

> **覆盖范围：** 2026-09 加入 main 的 cards

## 本月概览

9 月新加的几张卡，被测的东西从“agent 这一趟跑得怎么样”挪到了 agent 周围的东西上：一个是 agent 干活用的 harness，一个是 agent 提想法之前自己攒的那份文献。两个 harness benchmark 都在问同一件事：换掉一个不由 agent 决定的条件，比如能用的能力越加越多，或者换一个执行模型，之前的提升还在不在。那个出 idea 的 benchmark 问的是：让 agent 自己去找该读的文献，基于文献打分的 critic 看到的结果会不会变。

这个月量不大。进 `main` 的一共三张卡，都是 9 月当月发布的，所以这期只讲两条线，不硬凑成一个趋势。

## 这个月到底变了什么

### Harness 本身成了要交的作业

仓库里以前的 harness benchmark，大多是把 scaffold 固定住，在里面比模型；或者让优化器去改 harness，再报下游涨了多少。9 月这两张卡换了被打分的那一头。

[HarnessDev](../../works/harnessdev.md) 让模型自己把执行软件搭出来。起点是一个能跑、但没有解题策略的种子程序，外加一到三个开发样例；搭好的 harness 先冻结，再交给执行模型去做下游任务，其中包括 MLE-bench 的比赛题。编写者和执行者分开了，同一个 harness 就既能配它的编写模型测，也能配统一的运行模型测。结果有好有坏，这恰恰有用：不同版本之间提升幅度不一样，换成没见过的任务或换个执行模型，提升就缩水；报的 token 效率也只算执行，不算开发花的成本。

[EvoHarnessBench](../../works/evoharnessbench.md) 是从外面动 harness。17 条任务流，每条三到六个阶段，一路往里加工具、skill 或专门的 agent，前面阶段的任务原样保留。这么设计，就把一个准确率数字里搅在一起的两件事拆开了：能力菜单变长以后，agent 老任务还做不做得对；新能力本来要解决的新任务，适应以后有没有帮上忙。它的边界也写得很明白：能力只加不减，删掉或改动能力的情况没测。

两张卡放一块看，说的是 harness 也会退步。它们都没证明 harness 上的改进能普遍迁移，反倒都把迁移不过去的地方报了出来。

### 该读啥，谁说了算

[AgentIdeaBench](../../works/agentideabench.md) 在输出格式和 critic 都一样的前提下，比了两种提出科学假设的办法：一种是直接拿到一份整理好的阅读清单，另一种是自己去找文献。Critic 判断新颖性之前会先检索已有工作，不光靠 judge 模型自己记得的东西。论文报告的结果是：自己找文献以后，可行性、清晰度和具体程度都上去了，但测出来的新颖性没有显著提升。这些结论能推多远，要看它的限制：分数都是模型判的，只在 100 对计算机科学假设上核对过和人的一致性；假设从来没拿实验验证过；而且 Active 条件一下子同时改了检索控制、多轮交互和工具使用三样东西。

## 值得展开的 Topic

[Agent Harnesses & Scaffolding](../../topics/agent_harnesses_scaffolding.md) 和 [Resource-aware Evaluation](../../topics/resource_aware_evaluation.md) 这个月一起动，原因很具体。Harness 一旦成了被打分的东西，它的成本就得和模型的成本分开报：HarnessDev 报了执行模型的 token，但没算编写模型开发时用的 token；EvoHarnessBench 在记保留率的同时，也记了 token、工具调用次数和延迟。[Skill Learning & Evolution](../../topics/skill_learning_evolution.md) 是从 EvoHarnessBench 的适应划分进来的：进入下一阶段之前，持久保存的产物要先从单独的样例里学出来。

在 [Evaluator Reliability & Validation](../../topics/evaluator_reliability_validation.md) 这边，AgentIdeaBench 的贡献是在 critic 里加了一步检索，再配一个小规模的人工一致性研究（和人类多数意见一致 77%，Cohen kappa 0.55）。计算机科学以外的学科，critic 没有验证过。
