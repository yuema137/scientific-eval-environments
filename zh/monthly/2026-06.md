# 2026-06 月度报告

> [English](../../monthly/2026-06.md) | **简体中文**

> **覆盖范围：** 2026-06 首次公开的工作

## 本月概览

2026 年 6 月是一个很关键的月：这时候仓库前面刚扩出来的 scope，开始不像“先把 topic 开着，后面再慢慢填”，而是真有结构支撑了。表面上看是 36 项工作很多，但更重要的是，这批新文献已经不再像一排平铺的 benchmark 名单。你能同时看到三条主线长出来：scientific benchmark 更贴近真实 workflow 和可执行产物；skill 开始变成一层可以单独评、单独诊断的对象；process-level evaluation 也不再是泛泛而谈，而是开始落到 validator、rubric、planning step 这些真能卡住系统的控制点上。

这一个月还把一件事讲得很透：只看最后成没成，已经不够了。无论是结构分析、工业过程控制、学术信息检索、软件工程，还是可复用 skill，大家都在强调同一个问题：如果 evaluator 说不清是哪一步坏了、缺的是哪层 subskill、或者是哪道校验挡住了坏动作，那这个 benchmark 最多只能排个名次，没法真正指导下一步改系统。

## 这个月到底变了什么

### [Scientific Agent Benchmarks](../../topics/scientific_agents.md)

这个月 scientific benchmark 最明显的变化，是它不再满足于“拿一个带领域词汇的问题问模型，再给文本答案打分”。真正往前走的一步，是把评测对象往那个学科实际关心的产物或流程上推。[Agentic Large Language Models for Automated Structural Analysis of 3D Frame Systems](../../works/agentic-large-language-models-for-automated-struct.md) 不是问模型会不会聊结构，而是看它能不能写出可执行的 SAP2000 脚本，而且脚本跑出来的监测响应要压进 ground-truth 模型 1% 以内。[A Case Study of Evaluating AI Agents on a Neuroscience Data-to-Discovery Pipeline](../../works/a-case-study-of-evaluating-ai-agents-on-a-neurosci.md) 也一样，它评的是一条真实果蝇光遗传学研究流水线里本来靠人手工搭起来的软件工程环节。[ALeRCE Text-to-SQL](../../works/alerce-text-to-sql.md) 虽然规模不大，但路子很正：评的是天文学家真实会查的数据库，不是换了术语皮的通用题。

同时，这个月也在提醒一件事：所谓“更真实”，不只是多塞点领域名词，而是要把 agent 周围真正的控制边界也评进去。[Autonomous Action Execution (AAE) Framework](../../works/aae-framework.md) 很典型，它的 LLM 根本不能直接下手操作，所有提议都要先过确定性 validator，而且 validator 还得沿着装置 P&ID 拓扑去审。再加上 [PowerAgentBench-SS](../../works/poweragentbench-ss.md)、[PDAgent-Bench](../../works/pdagent-bench.md)、[GeoNatureAgent Benchmark](../../works/geonatureagent-benchmark.md)、[ScholarQuest](../../works/scholarquest.md)、[NatureBench](../../works/naturebench.md)、[PhySciBench](../../works/physcibench.md) 这些工作放一块看，6 月已经很像一个分水岭：field-specific evaluation 不再满足于静态 QA 代理指标了。

还有一条没那么喧闹、但很关键的线：benchmark 自己也开始被当成一个需要认真设计的对象。[FrontierCode](../../works/frontiercode.md) 和 [GeneBench-Pro](../../works/genebench-pro.md) 明确把 validity 和 contamination 摆上来；[Curation-Bench](../../works/curation-bench.md) 则更进一步，让 benchmark 直接卷进 data improvement loop；[SciAgentArena](../../works/sciagentarena.md)、[scBench-Long](../../works/scbench-long.md)、[Agents' Last Exam](../../works/agents-last-exam.md) 又把 long-horizon 和难度校准这条线往前推。合起来看，这个月的核心不只是“agent 能干啥”，而是“如果你真想拿 evaluation 来指导开发，那 evaluator 本身得长成什么样”。

### [Skill Hierarchy](../../topics/skill_hierarchy.md)

6 月的 skill 文献，比“agent 会不会用 skill”这种泛泛说法具体得多。真正的变化是：skill 开始变成一个可以被单独测量的对象。[A Framework for Evaluating Agentic Skills at Scale](../../works/a-framework-for-evaluating-agentic-skills-at-scale.md) 把 skill 仓库变成可执行任务，再大规模打分；[Skill Coverage](../../works/skill-coverage.md) 和 [SkillJuror](../../works/skilljuror.md) 则分别盯住两件互补的事：agent 到底有没有覆盖到 skill 里承诺的行为约束，以及同一份知识换一种组织方式，实际表现会不会跟着变。

另一些工作则是把原来糊成一团的能力层次拆开。[ATOM-Bench](../../works/atom-bench.md) 把机器人里的 atomic competence 和 compositional competence 分开，于是失败到底是底层 primitive 没练好，还是复用/组合本身出了问题，就不再含糊。[PDAgent-Bench](../../works/pdagent-bench.md) 在 VLSI physical design 上也干了类似的事：概念题、工具题、闭环 workflow execution 不是一个层级，混成一个分数没法指导改进。[SCR-Bench](../../works/scr-bench.md)、[SkillAudit](../../works/skillaudit.md)、[RubricsTree](../../works/rubricstree.md) 从不同角度都在强化同一个判断：如果你真想改 reusable agent behavior，evaluator 就得指出 skill stack 里到底是哪一层坏了。

[Agent Skill Evaluation and Evolution: Frameworks and Benchmarks](../../works/agent-skill-evaluation-survey.md) 这篇综述在这里有用，不是因为它把文献念了一遍，而是因为它让这个月看上去零散的 skill papers 连成了一条线。到 6 月底，Skill Hierarchy 已经不像一个顺手打上的标签，它更像一个稳定成形的评估问题。

### [Trajectory Evaluation](../../topics/trajectory_evaluation.md)

如果说 6 月有一个特别干净的概念中心，那就是：trajectory 不再只是 debug 残留物，而开始变成主要证据对象。[AISE-Bench](../../works/aise-bench.md) 不只给答案，还给全 API trajectory 和校验过的参数；[RigorBench](../../works/rigorbench.md) 直接从执行轨迹里给工程过程纪律打分；[TELBench](../../works/telbench.md) 和 [QVal](../../works/qval.md) 继续把分数往中间步骤里压；[AAE Framework](../../works/aae-framework.md) 更是把“提了什么动作”和“哪些动作被 validator 挡掉了”本身也纳入评测对象。

这条线重要，是因为这个月一再暴露 outcome-only evaluation 的同一个短板。一个系统可以最后做成，但过程里可能 planning 很脆、动作提议不安全、skill 用得很差、工程纪律也很散；反过来，一个系统也可能在后段翻车，但前面其实做对了好几步，二值结果会把这些全扔掉。6 月 trajectory work 的价值，不在某一篇 paper 单独多强，而在它们合起来把一句话讲实了：如果 evaluator 看不见中间状态、看不见选了哪个 tool、看不见 validator 介入、看不见漏掉了哪条 skill 约束，那它还不够格当 development signal。

## 值得展开的 Topic

6 月是这份档案里第一次让 [Scientific Agent Benchmarks](../../topics/scientific_agents.md)、[Skill Hierarchy](../../topics/skill_hierarchy.md)、[Trajectory Evaluation](../../topics/trajectory_evaluation.md) 看起来不是“刚好同时出现”，而是真的缠在一起。很多 paper 会跨这几页，不是因为标签乱贴，而是因为仓库前面那条总 thesis 开始有了实证支撑：evaluation 不只是最后量一下 agent 好不好，更是把系统结构摊开，好让你知道下一步该改哪儿。
