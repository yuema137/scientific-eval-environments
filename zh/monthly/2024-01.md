## 本月概览

- 本月共有 **1 项工作**进入知识库：**1 项当月新发布**，**0 项历史补录**。这项就是 [AgentBoard](../../works/agentboard.md)，2024-01-24 首次公开。
- 它的主张不大，但压得住：一个多轮 agent 到底是怎么失败的，二元成功率根本看不出来。所以评测不该只盯着最后成没成，得把中间走了多远也记下来。
- 做法是给子目标做标注。每个任务都配一串子目标，主指标就是完成了多少；一条轨迹哪怕最后没成，走过的那段照样能拿到分。
- 代价说得很明白，也很实在：子目标是人一条一条手写的，所以覆盖面能铺多快，全看人工拆解跟不跟得上。

## 这个月到底变了什么

**对多轮 agent 来说，二元成功率不再是唯一的分数。** 先看大多数 agent benchmark 是怎么打分的：只认最后任务成没成。在一个部分可观测、还得多轮交互的任务里，一个 agent 五步里做完了四步，最后栽在一个致命错误上，另一个压根没找对任务，两个在成功率上都只算一次失败。这么一压平，恰好把诊断型评测最想知道的两件事给盖住了：这个 agent 到底有没有真进展，还有它是在第几步卡住的。

[AgentBoard](../../works/agentboard.md) 换掉的，是它去测量的那个量。它一共 1,013 个环境（九种任务类型，归成 embodied、game、web、tool-use 四个家族），每一个都标了一条子目标链；benchmark 会上报一个 **progress rate（进度率）**，也就是一条轨迹里够到了多少比例的子目标。要点是：它没把二元成功率扔掉，成功率还留着当一条粗一点的基线，方便跟以前的 benchmark 对比；progress rate 是拿来补充的，不是取而代之。拿一个卡住的 agent 走一遍就明白了：在成功率下，它跟一个压根没起步的 agent 分不出来；在 progress rate 下，它按完成了几个子目标来拿分，配套那块分析看板，还能按任务家族和能力维度把结果拆开看，而不是只给各家系统排个名次。

不过这套做法有个明确的边界。progress rate 能做到多准，取决于它背后那套子目标拆解有多好；而这套拆解是人一条一条手写出来的。真正卡住的是扩展：想把 benchmark 铺到一个新的任务家族，就得有人重新去标注，自动推不出来。

## 值得展开的 Topic

### [Trajectory Evaluation](../../topics/trajectory_evaluation.md)

AgentBoard 是本月落在这个 Topic 下的工作，本月的叙事也主要从它讲起：它把 prompt 到结果之间的这条路径整个留了下来，没有压成一个标签。在这个 Topic 里，它立起来的是**基于子目标**的这条设计路线，每条轨迹都标上一串子目标，主打指标就是完成了多少。就这么一改，评测才分得清「走了一大段」和「压根没成」这两种情况，而二元结果根本表达不出这个差别；那块分析看板也顺势把留下来的轨迹变成了一份诊断材料，而不是排行榜上的一行。

同样这套子目标进度的机制，还让它挨着两个相邻 Topic，这里只做交叉链接，不重复展开：

- [Skill Hierarchy](../../topics/skill_hierarchy.md)：每个任务自带的那条子目标链，可以当成一份按子目标切分的能力信号；这套拆解是落在单个任务身上的，不是落在那种跨任务共享的能力上。
- [Credit Assignment](../../topics/credit_assignment.md)：按完成的子目标来给分，其实是在回答一个很具体的问题，就是奖励到底该落在轨迹的哪一处。它给的答案是落到每个子目标上，而不是按打分的子任务、也不是按轨迹整体的某个维度来分。
