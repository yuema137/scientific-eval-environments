# 2024 年 8 月月度报告

> [English](../../monthly/2024-08.md) | **简体中文**

> **覆盖范围：** 2024-08 首次公开的工作

## 本月概览

- 本月共有 **4 项工作**进入知识库：**4 项当月新发布**，**0 项历史补录**。分别是 [TransportBench](../../works/transportbench.md)（2024-08-15 首次公开）、[BLADE](../../works/blade.md)（2024-08-19）、[SimBench](../../works/simbench.md)（2024-08-21）和 [PEOA](../../works/peoa.md)（2024-08-23）。
- 这四项全是面向具体领域的科学或工程 agent benchmark，也都挂在同一个 Topic [Scientific Agent Benchmarks](../../topics/scientific_agents.md) 底下；可没有哪两项冲着同一个领域去：交通工程、数据驱动的科学、多物理场仿真，还有化工与过程工程。
- 本月大家真正较劲的，不是*哪个模型赢*，而是*一个评测器到底该打什么分*。这四项在实践里意见并不一致：两项给一道教科书式的最终答案打分，一项给答案背后的分析决策打分，还有一项给一条多轮搭仿真器的轨迹打分。
- 分界线在于这个 agent 有没有真的去碰那个科学对象。TransportBench 和 PEOA 打的是静态问答的分；BLADE 让 agent 跟数据打交道；SimBench 让它们分好几轮搭出一个能跑起来的仿真。

## 这个月到底变了什么

**这个月，科学 agent 评测一下子铺到了四个互不相干的领域上，而真正有意思的差别，落在评测目标上，不在排行榜上。** 先看给一个领域 LLM 打分，惯常的省事办法是什么：收一批本专业的题，只对最后的答案。这法子便宜，但它只能证明模型给出了一个看着靠谱的答案，证明不了背后的推理、或者那套分析过程站不站得住。2024 年 8 月新进来的这四项，都在从各自不同的方向跟这条捷径对着来；把它们摆一块儿读，恰好能把一个 benchmark 平时揉在一起的两个维度拆开：*到底在给什么打分*，还有*这个 agent 有没有真去碰那个对象*。

**先说「给什么打分」这条轴，本月从「只打最终答案」一路铺到「打过程」。** [TransportBench](../../works/transportbench.md) 打分的对象还是最终答案，但它请领域里的人类专家，在 140 道本科阶段的交通工程题上，把答案和答案背后的推理一起评；然后又加了两条排行榜不会有的轴，一条是同一题反复做几遍答案稳不稳，另一条是追问一句「请仔细核对你的解答」之后模型稳不稳。正是这份额外的较真，才把它那个招牌结论逼了出来：准确率和自我核查时的稳定性，是两码事。Claude 3.5 Sonnet 在准确率上领先（67.1%，94/140），可一旦让它复核，它反而把最多的原本做对的答案给推翻了（改了 16 道，而 GPT-4 和 GPT-4o 只改了 4 到 6 道），所以一个模型的招牌分数，并不能预示它在行为上稳不稳。[PEOA](../../works/peoa.md) 更进一步，把打分拆到工具学习的四个阶段上，planning、tool selection、tool calling、response generation，这样一次失败就能定位到轨迹在哪一步断的，而不是塌成一个末端任务的总分。[BLADE](../../works/blade.md) 干脆把「单一答案」整个扔了：数据驱动的科学本来就容得下好几种都站得住的分析，所以它评的是一个 agent 做出的*分析决策*，也就是它挑了哪些概念构念、做了哪些数据变换、选了哪些统计模型，拿去跟专业数据科学家各自独立做的分析比，报的是这些选择的多样性，而不是一个准确率数字。

**再说「agent 有没有真去碰那个对象」这条轴，本月从纯文本问答，一路铺到交互式地搭仿真器。** TransportBench 把话说得很明白，它就是个静态文本 benchmark，流程里没有工具调用、没有代码执行、也没有仿真器；它甚至把原题里的图都换成了文字描述，好让这道测验变成纯粹的语言推理。PEOA 的题目同样是教科书式的问答对，所以它量的是过程工程里的*计算*，而不是那种真能跑的过程系统工作，比如搭流程图（flowsheet）、或者把仿真器接进环路里做设计。BLADE 往里挪了一步：它的发现恰恰是，那些*会去跟底层数据打交道*的 agent，在分析选择的多样性上比基础语言模型有改善（虽然还没到最优），这样一来，「跟数据打交道」这件事本身就成了被测的变量。[SimBench](../../works/simbench.md) 待在最远的那一头，它让 33 个以上面向仿真的 LLM，通过多轮对话，为开源的 Chrono 多物理场仿真器立起一个能用的数字孪生（digital twin），打分由一个 LLM judge 按预先定好的规则、再带上人工在环的引导来完成，所以它评的技能是反复迭代地生成仿真器代码，而不是一次性把脚本写出来。

**本月这几处要当心的地方，都聚在评测有效性上，值得往后带着，而不是抹平了事。** PEOA 拿同一批 MathComp 和 ChemProc 数据集，既用来对框架做 instruction-tune、又用来评测（70/15/15 划分），所以它跟商用基线咬得那么近，其实是在拿一个领域内微调过的系统，去比那些在微调分布上做零样本的模型；而且它 response generation 那一阶段靠的是表面重合类的指标（BLEU、ROUGE-L、Exact Match），这些指标对数值对不对来说，只是很弱的替身。TransportBench 是本科难度，而且题目分布不均（光公共交通就占了 140 道里的 55 道），再加上它把图换成文字这一步，把几何设计题和网络题里本来绕不开的读图那部分给抹掉了。SimBench 的卡片是照着 arXiv 摘要和官方项目材料整理出来的，里头的数值排名还得等全文来核。这些都不至于让结论作废，但它们框定了每个结果到底能说多大的话。

## 值得展开的 Topic

### [Scientific Agent Benchmarks](../../topics/scientific_agents.md)

本月这四项工作，在这里都是主要参考，它们合在一起，正好说清了这个 Topic 的核心主张：一个科学 agent 的产出，得锚在一个跟领域对得上的检查上，而不是光看表面像不像。它们之间的区别，在于这个锚往下扎得有多深，这也正是上面讲过的那条谱系。

- [TransportBench](../../works/transportbench.md) 给这个 Topic 补上了一个它之前没覆盖的领域，交通系统工程，这门课是放在土木工程培养方案里教的；它把「对不对」锚在人类专家对 140 道课程题的评分上，而不是靠自动字符串匹配、也不是靠一个 LLM judge。它对这个 Topic 的贡献，既是补了个新领域，方法上也有分量：它把准确率、多次重复的一致性、自我核查时的稳定性拆成三条独立的轴来量，摆出了一个准确率排名和稳健性排名会倒过来的例子，而这种情况，一个只给单一分数的 benchmark 是藏得住的。它的边界是：这是一个静态、单轮、纯文本的测验，流程里没有工具调用、没有代码、也没有交通仿真器，作者把会用工具的 agent 列进了未来工作。

- [BLADE](../../works/blade.md) 冲的是数据驱动的科学，它把锚从答案挪到了分析过程上。一个针对真实数据的研究问题，本来就容得下好多种都站得住的分析，所以它评的是一个 agent 选了哪些构念、做了哪些变换、用了哪些统计模型，拿去跟专家各自独立做的分析比，并且把「站得住的选择有多少样」这份多样性当成一个头等重要的量来对待。它报出来的结果是：会跟数据打交道的 agent，相比基础语言模型在多样性上有改善，但还够不到专家的水平，这一点，恰好成了这个 Topic 那个主张的证据，也就是「真去碰那个对象，会改变 agent 的行为」。它的边界在范围上：论文里的数字是 12 个数据集（仓库里列得更多），而且这套评测覆盖的是在这些数据集上的分析判断，不是端到端的科学自动化。

- [SimBench](../../works/simbench.md) 是本月交互性最明确的一例：为 Chrono 多物理场仿真器做多轮的数字孪生生成，覆盖五个物理领域（多体动力学、有限元分析、车辆动力学、机器人动力学，还有传感器仿真），打分由一个按规则引导的 LLM judge 加上人工把关来完成。它把多轮的仿真器代码搭建，也就是把几何、动力学、求解器配置打包成一份交付物，立成了被评测的技能；而且它由 Chrono 的开发者维护，所以任务能跟真实的仿真器一直对得上。它这个月的边界在验证上：卡片是靠摘要和项目材料撑起来的，那些数值上的模型排名，还得等全文。

- [PEOA](../../works/peoa.md) 贡献的是一个化工与过程工程的框架，配着两个数据集一起放出来（MathComp，8,500 多个问答对；ChemProc，7,000 多个问答对），还有一套按阶段拆开的评测协议。在这个 Topic 里，它最与众不同的一手，是打分「看轨迹」，而不是只看末端答案，正是这个性质，让它同时挨着两条相邻的轴：
  - 在 [Trajectory Evaluation](../../topics/trajectory_evaluation.md) 上，那套四阶段的指标（planning、tool selection、tool calling、response generation）把中间的工具使用决策，拿去跟标准计划和真实工具集比着打分，从而定位到一条轨迹在哪儿断的，而不是只报一个数字。
  - 在 [Skill Hierarchy](../../topics/skill_hierarchy.md) 上，那套「元 agent 管着一群专家」的设计，一个协调者把查询拆成子任务、再把每个子任务分派给一个 instruction-tune 过的小规模专家模型，正是「把一个复杂任务，摊到一层层更窄的技能上」的一个具体例子。

  PEOA 的那些边界，在*这个月到底变了什么*里已经讲全了：微调和评测共用一批数据、生成阶段用的是表面重合类指标，还有那些教科书式的题目，测的是计算，而不是真能跑的过程系统任务。
