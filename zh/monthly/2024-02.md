# 2024 年 2 月月度报告

> [English](../../monthly/2024-02.md) | **简体中文**

> **覆盖范围：** 2024-02 首次公开的工作

## 本月概览

- 本月共有 **2 项工作**进入知识库，全是**当月新发布**，没有历史补录：一个是 [TravelPlanner](../../works/travelplanner.md)，2024-02-02 首次公开；另一个是 [LoTa-Bench](../../works/lota-bench.md)，2024-02-13 首次公开。
- 这两项工作站在「planning」这条轴的两头，却得出了同一个结论：agent 拿出来的 plan，该看它跑起来行不行，而不是拿它去跟一份参考答案比。两家都把 planner 的评测改成了靠执行来判定，而且全程自动。
- 这就换掉了两种更弱的信号。TravelPlanner 用确定性脚本去查约束满不满足，不看表面相似度，也不找 LLM 当裁判；LoTa-Bench 把 plan 丢进模拟器里真跑一遍，不再靠人去逐条看 plan。
- 只要有自动打出来的分，它暴露的差距就很扎眼：在 TravelPlanner 上，GPT-4 配 ReAct 最终通过率只有 0.6%，可它交出一份 plan 的次数其实高得多。
- 这两项都没落进任何一个标准的 science 或 engineering domain：一个待在具身家居模拟器里，另一个待在封闭的旅行沙盒里，所以本月没有 domain 这一节。

## 这个月到底变了什么

**planner 的评测从「比对」转向「执行」，而自动打出来的分，直接把 agent 差得有多远给亮了出来。** 先看老办法是怎么评判语言模型 planner 的：它总是拿一份 plan 去比另一样东西，要么是人去读这份提出来的 plan，要么是看它跟参考 plan 对不对得上。这条路能确认 plan 看着对，却确认不了它真能跑通；而且太靠人工，想大批量地扫模型、扫 prompt 根本铺不开。2024 年 2 月来了两个 benchmark，都把「比对」换成了「执行」，只是两者出发的底子很不一样，奔的却是同一个想法。

[TravelPlanner](../../works/travelplanner.md) 把一个多来源的大数据库冻进了一个封闭沙盒：3,827,361 条航班记录，再加上城市、距离、餐厅、景点和住宿数据。然后它让一个语言 agent 去这个库里搜，把有用的结果记住，再拼出一份可行的三天、五天或七天行程，一共覆盖 1,225 个精挑过的旅行意图。这里的成功，不是跟一份标准答案 plan 有多像。确定性脚本会去查几类东西：像交通不可用这样的环境约束、八条常识要求，还有覆盖预算、房间、菜系和交通的明确用户约束；而 Final Pass 这个指标，要求所有适用的检查同时全过。真正把差距摆到明面上的，是这个自动分：GPT-4 配 ReAct 最终通过率只有 0.6%，可它交出一份 plan 的次数其实高得多。这就把失败定位在了约束满足上，而不是「压根没产出东西」。

[LoTa-Bench](../../works/lota-bench.md) 在具身任务规划这边，合上了同一个「从人工检查到执行」的环。LLM 针对一条家庭服务指令提出一串技能序列，模拟器把它跑起来，成功与否就对着目标条件自动判分。这一套是在两组相互独立的「数据集加模拟器」上做的：一组是跑在 AI2-THOR 上的 ALFRED，另一组是跑在 VirtualHome 上、扩展过的 Watch-And-Help。用两组栈，是为了不让结论被某一个模拟器的怪脾气带偏；而自动判目标，让换模型、换 prompt 的消融实验便宜到能大批量地跑，搁以前这活儿只能靠人定性地看。

两项工作停在同一条边界上，分两个方面看。头一个是覆盖面：TravelPlanner 的沙盒是静态的，而且只管旅行，所以它测不了开放世界里的变化，也测不了别的规划领域；它那个严格的 Final Pass，还得靠各个分项指标才能把检索失败、完成失败和约束失败分开。LoTa-Bench 只有模拟，没有真实机器人；而且它确切的任务数和模型数还得等全文来核实，因为这张卡是照着摘要和官方仓库整理出来的。第二个方面是「到底测的是什么」：两家都只看执行出来的结果达没达到目标，不看中间每一步的选择是不是当时能做的最优那一个。这个区别，下面的 Topic 小节会讲明白。

## 值得展开的 Topic

### [Planning & Decision-Making Evaluation](../../topics/planning_decision_evaluation.md)

这两项工作都放在这里讲，是因为对它俩来说，planning 才是更锋利的那面镜子；而且它们合在一起，标出了这个 Topic 里一个很具体的动作：判断有效与否的信号，来自把 plan 跑起来，而不是拿它去对答案。这么选是有代价的，这个 Topic 对这一点很上心。因为分数是靠执行给出来的，这两个 benchmark 都没法把 planning 和 execution 拆开：一份本来靠谱的 plan，也可能因为某个工具什么都没返回、或者模拟器卡了壳而失败，而两家都把这算作一次失败。所以它们回答的是「这份 plan 跑通了没」，不是「这是不是最好的那份 plan」。在这个 Topic 的对比表里，TravelPlanner 和 LoTa-Bench 都落在「没做隔离」那一边，也都没有给出「换个方案会怎样」的反事实指标。

在这个限制之内，两家各自贡献的，是不同粒度的执行信号。TravelPlanner 会报各个分项约束的通过率：环境、常识和硬约束，再配上整份 plan 可不可行，这样读的人能看清是哪一类约束崩了，而不是只知道 plan 失败了；另外，搜索失败时环境还会返回反馈，所以能不能完成，得看 agent 会不会对着不可用的选项去调整，而不是光靠第一遍出的 plan。LoTa-Bench 则在它那两组模拟器栈上，报执行后目标达成的情况。也正是因为这个，两家都跟那种不带工具、靠对答案打分的 planner 分道扬镳，比如 [NATURAL PLAN](../../works/natural-plan.md)：后者把每个事实都直接给在上下文里，把执行这个混淆因素给撤了。而 2 月这两项工作是故意把执行留在环里的，代价就是归因上会含糊：一份差 plan，和一份本来不错、却在下游栽了的好 plan，这俩分不太清。

### [General Long-Horizon Agent Benchmarks](../../topics/long_horizon_evaluation.md)

换到 horizon（长程）这条轴上看，这两项工作测的，是 planning 那面镜子照不到的东西：一个 agent 能不能把一个任务扛过许多前后相扣的步骤，而这些步骤里，早先的动作会改变后面的状态。TravelPlanner 跑的是交互式轨迹，步数上限 30 步，工具检索和环境反馈是穿插着来的，所以一次搜索失败会逼着 agent 记住自己已经查到了什么，再去改；能不能完成，靠的是把这个循环撑下去，不是靠某一次回答。LoTa-Bench 贡献的是多步技能序列的 plan，一路执行到目标达成，而其中每个技能产生的效果，都决定了下一个技能能干什么。两家都没加那种密集的中间进度指标，判分都落在最终目标上；也正因为这样，这两项工作里「选择质量」那层读法，留在上面的 [Planning & Decision-Making Evaluation](../../topics/planning_decision_evaluation.md) 里讲，这里就不重复了。
