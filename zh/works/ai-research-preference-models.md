# AI Research Preference Models (2026)

> [English](../../works/ai-research-preference-models.md) | **简体中文**

## Overview

AI Research Preference Models（RPM）预测 AI 研究 agent 提出的哪些候选方案值得花 GPU 时间跑一遍，好把固定的执行预算花在最可能有回报的候选上。两个变体都建立在冻结的预训练语言模型之上、不做任何任务特定训练——一个只对方案与代码作推理，另一个会先跑小规模试点实验——并双双接入 AIRA-dojo 搜索 agent，在 AIRS-Bench 上测量。

## Summary

问题的出发点是一处成本上的不对称：AI 研究 agent 几分钟就能写出一个候选方案，但要弄清它管不管用，得花上数小时乃至数天的 GPU 时间。于是 agent 提出的候选永远多过它跑得起的数量，这就使它的**研究偏好**——如何在候选之间分配固定的执行预算——成为一个独立于「能否想出好点子」的进展决定因素。RPM 提供的正是这种偏好。只读式变体对候选方案、候选代码，以及此前已执行方案及其验证分数作推理，一次实验都不跑就作出取舍。agentic 变体则额外拿到执行环境的沙箱副本，先跑小规模试点实验——一个可用 python、bash 与提交工具的多轮 agent，上限五分钟——再作决定。两者都被接入 AIRA-dojo 的子节点生成环节；该搜索在 Draft、Improve 与 Debug 三类算子下每步生成 15 个候选。结果既报告为分数提升，也报告为预算节省，论文还测量了自己的选择离 oracle 还差多远。

## Tasks

评测底座是 **[AIRS-Bench](./airs-bench.md)**：**20 个公开发布的文本与表格任务**，覆盖语言建模、数学、生物信息学与时间序列预测。表现以逐任务的**归一化分数**给出，`NS = [φ(s) − φ(s_min)] / [φ(s_sota) − φ(s_min)]`，其中 **NS = 0** 为最低基线、**NS = 1** 为公开最好水平——正是这一点让指标各异的任务之间变得可比。

宿主 agent 是 **AIRA-dojo**，一个演化式树搜索框架：贪心的父节点选择总是对当前验证分数最高的节点做变异，每步生成 **N = 15** 个候选方案，最终提交整棵树中验证分数最高的那个节点。

## Domains

**AI & Machine Learning Research。** 被挑选的对象是机器学习研究工作——由留出集任务表现评判的模型与训练改动——而贡献完全以 AIRS-Bench 归一化分数衡量。不指派科学类共同领域：AIRS-Bench 本身确实跨到生物信息学与数学，但本文没有给出其 20 个任务的分领域构成，而它点名的两个逐任务结果（WinoGrande、SVAMP）是单个任务，而非有明确规模的领域切片。

## Evaluation

端到端结果基于**每任务单张 H200 跑 24 小时、10 个随机种子、20 个任务——合计 200 H200 GPU 小时**：

| 配置 | 归一化分数 | 追平基线所需墙钟时间 |
|---|---|---|
| 未引导的 AIRA-dojo（无 RPM） | **0.684** | 24 小时 |
| 只读式 RPM | **0.711** | 14.88 小时（1.61 倍加速） |
| agentic 式 RPM | **0.729** | 15.50 小时（1.55 倍加速） |
| 验证集 oracle 上界 | 0.748 | — |
| 测试集 oracle 上界 | 0.759 | — |

两个变体都在约 15 小时内追平未引导 agent 24 小时的表现，**所用执行预算不到后者的三分之二**。真正有信息量的是 oracle 那两行：agentic 式 RPM 的 0.729 已经吃掉了 0.684 → 0.748 之间的大部分差距，因此单靠改进选择还能剩下的余量并不多。

论文在两个 AIRS-Bench 任务上刷新了最好水平：**WinoGrande 94.1%**（此前 88.1%）与 **SVAMP 95.7%**（此前 94.2%）。

选择质量另行测量。相对随机的选择增益：随机约为 0.0，只读式更高，agentic 式最高；该增益与最终分数的相关性为 **Pearson r = 0.55、Spearman ρ = 0.56**。

一项在候选对上的离线评测比较了不同骨干模型：**GPT-5 64.66%**、**Gemini 3.1 Pro 67.40%**、**Claude Opus 4.8 67.44%**、**多数投票集成 68.04%**、**LLM 仲裁集成 69.35%**。端到端运行中，子节点生成与 RPM 骨干都使用 **Qwen3.6-27B**；提示词由 DSPy 的 MIPROv2 优化。

**没有任何人类或专家一致性测量**。离线的标准答案取自「子树最大值」标签——即某候选所在子树中出现过的最高测试分数——作者说明该标签继承了产生这棵树的贪心搜索策略所带来的偏倚，因为搜索过程本就偏爱早期分数较高的节点。

## Typical Duration

端到端运行为**每任务单张 H200 上 24 小时**，各跑 10 个随机种子。agentic 式 RPM 的试点实验限时**每次选择 5 分钟**。相对它所调度的预算，RPM 自身的推理很便宜：自托管的 Qwen3.6-27B 在每个 24 小时运行中增加 **0.66 小时**，即便把这部分延迟计入，分数仍有 0.708，而不计时为 0.711。

## Main Contribution

把预算分配确立为 AI 研究 agent 的一等杠杆，并证明一个不做任务特定训练的冻结预训练模型，就能把「哪些候选值得执行」预测得足够准，用不到三分之二的算力买到同样的结果——而且同时给出 oracle 上界，让单靠选择还剩多少余量一目了然。

## Key Design Ideas

- RPM 建立在冻结的预训练模型之上、**不做任务特定训练**，因此增益来自「这种预测本身可行」，而非来自对 benchmark 的拟合。
- 两个变体切出一组干净的权衡：对方案与代码作推理不花执行时间，跑试点实验则要付出真实的沙箱开销；两者都报告，等于给这份额外信息标了价。
- agentic 变体只用在 Draft 与 Improve 算子上，不用在 Debug 上——当任务是修一个已知的失败时，试点实验换不来多少信息。
- 报告验证集与测试集的 oracle 上界，把「我们的选择器更好」变成了「我们的选择器已经吃下了任何选择器所能拿到的大部分」，后者是强得多的论断形式。
- 选择增益既对照随机测量，又与最终结果作相关分析，因此选择质量是被验证为机制的，而不是从分数提升里默认出来的。
- RPM 的推理延迟被计入它所节省的预算（每 24 小时运行 0.66 小时），效率论断因而经得起自身开销的抵扣。
- 离线的骨干模型比较与集成实验与端到端论断分开陈述，作者也说明主要结论建立在端到端结果之上。

## Strengths

- 头条结果是在分数不变的前提下省下预算，这比在同等预算下提高分数是更难、也更有用的论断形式。
- 报告了 oracle 上界，读者因而能看出可获得的选择增益被吃掉了多少，以及剩下的余量其实很薄。
- 方法自身的开销被测量出来，并从它带来的收益中扣除，而不是排除在外。
- 作者标明自己的离线评测是 off-policy 且有偏的，并明确指出主要论断改以端到端结果为准。
- 子树最大值标签的偏倚被点名并作了解释，而不是含糊带过。
- 每任务 10 个种子、合计 200 H200 GPU 小时，对一个关于搜索效率的论断而言是相当扎实的评测规模——单种子结果会被方差淹没。

## Limitations

- 论文未说明代码或数据的发布位置（上文记为 `TODO(reference)`），因此这些 RPM 无法直接复用。
- 作者说明该方法只在 AIRA-dojo 的子节点选择环节、只用一个骨干模型（Qwen3.6-27B）、只在一个 benchmark 上得到验证，向其他脚手架与骨干模型的可移植性则留待后续工作。
- 把 RPM 用在最终节点选择而非子节点生成上时，相对普通的基于验证分数的选择几乎没有提升（附录 D），因此增益与「插在搜索的哪个位置」高度相关。
- agentic 变体需要一份执行环境的沙箱副本，这是只读式变体不必付出的实际部署成本。
- 离线评测的标准答案来自由「正在被改进的那个贪心策略」所产生的搜索树，因此离线的骨干模型排名并不是一次干净的测量。
- 全程没有使用任何人类或专家判断；选择质量只对照下游任务分数验证。
- Repository note: 论文的主要定位是一个**让 agent 变强的搜索组件**，而不是用来测量 agent 的工具，它也没有提出自己的 benchmark 或评分协议——评测用的是既有的 AIRS-Bench。本卡片将其归入 Resource-aware Evaluation，依据是「在固定执行预算下廉价预测方案质量」本身就是一个评估函数；这一归类是本仓库的判断，而非作者的。

## Related Works

- [AIRS-Bench](./airs-bench.md) — 本工作据以测量的 benchmark：上文所有数字所用的归一化分数，都来自这套机器学习研究任务集。
- [Beyond Final Scores](./beyond-final-scores.md) — 同样研究墙钟预算下的长时程 AI 研发，测的是 agent 如何花掉一次运行，而非去引导它花在哪里。
- [MLE-bench](./mle-bench.md) — 算力预算下的机器学习工程，预算只是限定运行时长，而非分配的对象。
- [SimulCost](./simulcost.md) — 成本感知评估，把所花算力与所得精度对照计分，在仿真调优上采用同样的「单位算力换多少精度」框架。
- [R³-Bench](./r3-bench.md) — 在候选题目之间分配共用预算，并对照由实际结果构造的 oracle 衡量——同一个「预算花得好不好」的问题，被做成了 benchmark 而非解成了方法。
