# ALeRCE Text-to-SQL (2026)

> [English](../../works/alerce-text-to-sql.md) | **简体中文**

## Overview

一套面向 ALeRCE 天文警报数据经纪人数据库的自然语言转 SQL 系统，随文发布了一个含 110 组自然语言/SQL 对的评测集——问题由天文学家提出，目标查询由专家撰写——并在其上以完全匹配的执行式指标比较了十三个 LLM。

## Summary

ALeRCE 是服务于 Zwicky Transient Facility 与 Vera C. Rubin Observatory 的社区警报数据经纪人，其数据库既大且不规整，不熟悉 SQL 的天文学家很难查得动。论文构建了一条四模块流水线——schema linking、查询分类、提示分解与自我纠错——把天文学家的问题转成可在该数据库上执行的 SQL；评测方式是同时执行预测查询与标准查询，比对返回的行与列。评测集的 110 组自然语言/SQL 对是从一线天文学家那里征集来的，而非合成生成，十三个 LLM 后端在其上打分，并附有逐模型的 API 成本表。核心结论是：当前 text-to-SQL 的最好水平并不能照搬到真实的科学数据库上——简单查询表现不错，一旦涉及连接和领域专有语义就急剧下滑。

## Tasks

ALeRCE 数据库上的 110 组自然语言/SQL 对。其中 21 组来自 ALeRCE 团队、曾在研讨会上展示过；其余 89 组由 10 位天文学家撰写，再由一位 SQL 专家为每组写出标准目标查询。数据对分为开发集 58 组（简单 32、中等 14、困难 12）与测试集 52 组（简单 32、中等 10、困难 10）。截至 2026 年初，目标数据库有 25 张表、304 个字段。

## Domains

天文学。该数据库是运行中的时域巡天警报经纪人，承接 ZTF 警报流（并将接入 Rubin/LSST），因此查询涉及的是天体、分类、测光与光变曲线属性；答对这些查询靠的是经纪人库表结构背后的领域语义，而不是通用的数据库推理。把它同时读作计算机科学也说得通——产出的是可执行 SQL，方法是一条 text-to-SQL 流水线——但受评的目标是检索出正确的天文记录。

## Evaluation

- **完全匹配（Perfect Match，PM）：** 预测查询与真值查询都被执行，比对二者结果；结果完全一致才算一次完全匹配。PM 对行标识（`PMrows`）与列标识（`PMcols`）分别计算，并针对每条查询相对真值集合另算精确率与召回率。
- **协议：** 每条查询在每个模型、每种生成方法下都跑 10 次，结果按简单/中等/困难三档难度标签拆分报告。
- **消融：** 直接（一次性）生成与逐步生成、以及带自我纠错模块的逐步生成相比较；直接推理在各难度档上都更差。
- **报告。** 共评测十三个模型：GPT-4o、GPT-4.1、GPT-5、GPT-5.2、GPT-5.2-Codex、GPT-5.3-Codex、Claude 3.7、Claude Sonnet 4.5、Claude Opus 4.6、Gemini 2.5 Flash、Gemini 2.5 Pro、Gemini 3 Flash 与 Gemini 3.1 Flash。最好的配置是 Claude Opus 4.6 配逐步生成加自我纠错，简单查询上 PMrows/PMcols 为 0.97/0.94，中等为 0.44/0.72，困难为 0.59/0.49。作者点名 Claude Opus 4.6、Gemini 2.5 Pro、Gemini 3 Flash 与 GPT-5.2-Codex 为总体表现最强的一组。

## Main Contribution

一条以领域为依托、面向真实天文警报经纪人数据库的 text-to-SQL 流水线，配套公开发布了由天文学家撰写的自然语言/SQL 评测集，并系统比较了十三个模型——结果表明，标准 benchmark 上所报告的 text-to-SQL 进展，并不能迁移到库表结构不规整、语义带领域专有性的科学数据库上。

## Key Design Ideas

- 拆成四个各自提示的模块——schema linking、查询分类、提示分解、自我纠错——每个模块各发一次 API 调用，从而能把失败归到具体阶段。
- 一个为查询分档的难度分类器，配上按难度分层的评测集，使准确率能对着查询复杂度报告，而不是被平均掉。
- 自我纠错的驱动方式是执行候选查询并把报错回灌，它能修好语法与库表引用类的失败，但修不了语义上的错误。
- 执行式评分拆成行一致与列一致两部分，把「选对了对象」与「返回了对的字段」区分开。
- 每条查询跑 10 次，使 LLM 生成的随机性被测量，而不是被假定掉。
- 在提示中显式注入领域知识，对应论文的发现：表现高度依赖于外部提供的库表结构与天文学背景。

## Strengths

- 评测集征集自 10 位一线天文学家以及经纪人团队，问题就是真实用户会问的，标准查询则由 SQL 专家撰写。
- 评分基于执行而非字符串匹配，并把行一级与列一级的正确性分开。
- 难度分层加上开发集与测试集的匹配划分，让性能随复杂度的衰减清晰可见。
- 十三个后端横跨三家厂商、数个代际，每个各跑 10 次，还配有逐阶段成本表，准确率与价格可以对照着读。
- 目标是服务 ZTF 与 Rubin 的在运行经纪人，而非合成的库表结构。

## Limitations

- 评测集偏小——总共 110 组，其中测试项只有 52 组，中等与困难各仅 10 组——各难度档的比率因而建立在极少的查询之上。
- 结果随难度并不单调（最好的模型在中等上 PMrows 为 0.44，困难上却是 0.59），而每档样本数太少，难以解读。
- 自我纠错能修好执行失败，却抓不出语义写错、但能干净执行的查询，因此 PM 仍可能出于错误的理由给分或扣分。
- Repository note: 该 benchmark 只覆盖一个数据库。它测的是模型能不能查 ALeRCE，而不是能不能查天文档案库这一大类。
- Repository note: 论文称这 110 组数据已公开提供，但预印本中未找到对应的仓库或归档链接。
- Repository note: 实质贡献是一套系统；之所以收录，是因为它同时发布了专家策划的评测集，并带有执行式评分协议与十三个模型的比较。
