## Overview

LLM-EPANET 是一条检索增强的多 agent 管线，把关于供水管网的自然语言问题转换成可执行的 EPANET 仿真代码；随之发布的还有一个含 69 条查询的精选 benchmark，每条查询的 ground truth 都是一份手写的确定性参考脚本。

## Summary

EPANET 是供水管网水力与水质行为的标准仿真器，但要越过其图形界面使用，就得针对它的工具包写代码，这让基于模型的分析局限在一小群专业人员手里。LLM-EPANET 检索 EPyT（EPANET 的 Python 封装）文档中函数级别的片段，提示 LLM 写出回答用户查询的 Python 函数，再由一个较小的模型构造求值调用，最后在隔离沙箱中执行，并带自动的自调试回路。评测集含 69 条查询，跨三个标准管网、五个复杂度类别；论文报告了分类别准确率、错误分类体系、提示词敏感性，以及七个商业 LLM 之间「精度–成本–时延」的对比。

## Tasks

69 条自然语言 benchmark 查询，覆盖三个管网——EPANET 原始发行版中的 Net1 与 Net3，以及 L-Town——分为五个复杂度递增的类别：**Static**（无需仿真，从管网文件即可作答）、**Hydraulics**（需要一次水力仿真）、**Quality**（需要一次水质仿真）、**Hydraulics Scenario**（先改动管网再仿真）与 **Iterative**（反复调整参数并作条件性的可行性检查）。每条查询按其所需的最复杂建模操作归类。Iterative 类别明确带探索性质，只有三条查询。benchmark 查询、期望答案与 ground-truth 脚本均以开源方式发布。

## Domains

土木与结构工程：市政供水管网上的水利基础设施工程——标准 benchmark 管网上的压力、流量、水泵能耗、管网改动与情景分析；作者来自土木与环境工程学院。水质类查询（余氯输移、水龄、水源追踪）也触及环境科学，但全程受评的对象始终是管道输配网络，而非天然水体。

## Evaluation

- 判的是返回结果的功能正确性，而非文本或代码相似度。每条 benchmark 查询都事先由人工针对 EPyT 写好参考实现并执行；这些确定性的参考输出即 ground truth，并以可执行的测试脚本形式发布。
- 只有返回值与参考结果等价，回答才算 *正确*。执行失败、未能恢复的错误、聚合方式错误、索引错误与单位不符都计为错误。当 LLM 输出与参考不同、但尚可视为等价时（四舍五入、标量与结构化输出之别），由一位水力建模专家裁定等价性，且不修改生成的代码。
- 准确率按类别报告，即答对的比例。
- **报告。** 共运行七个模型：`microsoft/phi-4`、`google/gemini-2.0-flash-001`、`qwen/qwen2.5-vl-72b-instruct`、`openai/gpt-4.1-mini`、`meta-llama/llama-4-maverick`、`anthropic/claude-3.7-sonnet` 与 `openai/o3-mini-high`。总体准确率在 56–81% 之间，所有模型在 Static 类别上都高于 90%；`o3-mini-high` 总体最高，为 80%，且在每个类别上都高于 60%。`phi-4` 在 69 条查询中有 40 条未能产出可执行代码。
- 论文还给出覆盖全部运行的失效分类：执行错误以签名不匹配（44.6%）与导入问题（23.8%）为主；答案错误则以索引错误（31.5%）、逻辑错误（25.9%）与聚合错误（20.4%）为主。

## Typical Duration

每条查询是一次「提示到执行」的单回合，最多五次自调试重试（报告的实验中设为 5）；最终成功的案例中超过 85% 在第一次尝试即达成，且没有模型靠第五次尝试多解出任何一条。沙箱执行设 60 秒超时上限。跑完 69 条查询一轮，`o3-mini-high` 的 LLM 用量约合 1 美元；论文把几个更便宜的模型列在「精度–成本」帕累托前沿上，这一开销是它们的四倍以上。单条查询的响应时间按模型报告，其中 `o3-mini-high` 明显最慢。

## Main Contribution

一个基于 agent、无需写代码的 EPANET 自然语言接口，把 EPyT 文档上的 RAG 与多 agent 代码生成、自调试管线结合起来；同时发布一个精选、公开的 69 条查询 benchmark，每条配可执行参考脚本，用于衡量现有 LLM 对供水管网建模任务的支持程度。

## Key Design Ideas

- ground truth 是每条查询一份可执行的参考脚本，评分因此可复现，且与 LLM 生成的代码无关——完全不用文本或代码相似度指标。
- 查询按其所需的最复杂建模操作分层，从静态查询到情景与迭代任务的准确率衰减因而一目了然。
- 文档按函数粒度切块，而非按 token 窗口切，使每个检索单元在语义上自成一体；检索质量本身也以成功运行中实际调用的函数为参照，用 precision/recall/F1 校验，K 固定为 5。
- 结构化的错误 traceback 会回喂给代码生成 agent，重试次数有上限，并把每多一次重试所换来的准确率增益报告为一条鲁棒性曲线。
- 作者把承载 EPANET/EPyT 建模惯例的元提示词当作可消融的显式组件：Basic、Simple 与 Complex 三种变体互相比较，越难的类别差距越大。
- 每个模型的成本与时延都与准确率并列报告，模型选择因此呈现为一种权衡，而非一份排名。

## Strengths

- benchmark 随附确定性、可执行的 ground truth，这在以仿真器为中介的自然语言任务里并不多见。
- 七个模型在同一套协议下比较，覆盖从开放权重到前沿商业的各个档次。
- 失效分析是定量且落到机理层面的（签名不匹配、下标从一开始还是从零开始、聚合方式），而不止一张准确率表。
- 通过三级元提示词消融，把提示词内容单列为一个变量。
- 物理由 EPANET 引擎强制满足，而非由模型近似，因此只要程序写对，所得结果就与人类建模者完全一致。

## Limitations

- 69 条查询规模偏小，Iterative 类别更只有三条，作者自陈这属探索性质，而非统计上稳健的估计。
- 对接近正确的答案，等价性裁定只由一位人类专家完成。
- 系统只按返回值是否与参考一致计分；作者指出它并不检查一个能跑通的解在水力上是否可行（负压、水池边界越限）。
- 论文声明其目的不是给 LLM 供应商排名，并提醒其模型排序只是一个时间切片；所选模型意在覆盖各成本档次，而非构成完整阵容。
- 系统表现高度依赖一条人工调优、注入领域知识的元提示词，作者认可这是有意的设计选择，而非自主推理能力的体现。
- Repository note: 三个管网都是 EPANET/L-Town 的标准示例，因此对公用事业规模或条件恶劣的真实管网文件的泛化能力未经检验。
