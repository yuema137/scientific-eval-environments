# Automating Structural Reliability Analysis with a Multi-Agent Large Language Model Framework (2026)

## Overview

A five-agent LLM framework that carries component-level structural reliability analysis from a natural-language problem statement to an interpreted reliability index and failure probability, released with a held-out 20-problem reliability benchmark whose reference solutions come from validated solvers and whose method-category labels come from a published deterministic criterion.

## Summary

Structural reliability analysis quantifies the probability that a building or piece of civil infrastructure exceeds a prescribed limit state, but running one requires expertise in probability theory, structural mechanics and numerical simulation simultaneously. The paper builds a multi-agent pipeline in which specialized LLM agents handle problem formulation, method planning, solver-code generation and result interpretation, while the reliability index β and failure probability P_f are produced only by a deterministic non-LLM runner executing validated solvers, so no numerical result is ever generated by a language model. The single hardest decision — choosing a priori which family of reliability methods will be accurate enough at acceptable cost — is isolated in a Method Planner, the only fine-tuned agent, adapted with QLoRA on 150 synthetic examples labelled by a deterministic reference criterion. Evaluation is on a held-out set of 20 hand-authored reliability problems disjoint from training, used both for end-to-end execution against reference solutions and for an independent comparison of three model configurations on method-category selection.

## Tasks

The held-out benchmark comprises 20 hand-authored component-level structural reliability problems, disjoint from the 150 synthetic examples used to fine-tune the Planner, constructed so that no single reliability method is uniformly suitable. Reported coverage: 11 probability distribution types (normal, lognormal, Gumbel, Weibull, Fréchet, Beta, chi-square, exponential, Rayleigh, Type-I and Type-III smallest), problem dimensions from 2 to 30 random variables, limit-state functions ranging from linear through mild to strong nonlinearity, and failure probabilities spanning common to rare events. Under the deterministic labeling rule the 20 problems split into 8 FORM-based, 6 MCS and 6 Advanced cases. The problems are named in the results table and are recognizably civil and structural: a resistance–load (R–S) case, beam yielding, concrete compression, Euler column buckling, an exponential ratio case, a trigonometric oscillator, Weibull fatigue, a rare containment event, a correlated pile group, a ten-variable offshore jacket, bounded (Beta) resistance, a Mohr–Coulomb slope, chi-square vibration, a Fréchet wind extreme, Rayleigh wave overtopping, a bridge girder under correlated loads, a 30-variable parallel system, Type-I smallest yield, a shifted Type-III smallest case, and exponential degradation. Each task is posed as a natural-language problem statement; the agent must extract the random variables with their distributions and parameters, the limit-state function and the correlation structure, select a method category, generate solver code, execute it, and interpret the result. The running example used throughout the paper is a slender steel column under Euler buckling (problem p04).

## Domains

Civil & Structural Engineering. The evaluated objective is reliability-based safety assessment of structural components and civil infrastructure — beam yielding, concrete compression, column buckling, bridge girders under correlated loads, an offshore jacket, a pile group, and a Mohr–Coulomb slope — with results interpreted against code target reliability levels such as the β = 3.8 ultimate-limit-state value in Eurocode EN 1990 over a 50-year reference period. This spans the domain's structural analysis, geotechnical engineering and design-code scope. The authors are in civil engineering departments at the University of Toronto, Seoul National University and Yonsei University. The problem set touches geotechnical (slope stability, pile group) and offshore (jacket structure, wave overtopping) cases, but these are individual items within a structural-reliability set rather than separate evaluated fields, so no Earth Science or Energy Systems co-domain is assigned.

## Evaluation

Two evaluations are run on the same held-out 20-problem set. **End-to-end execution**: a run counts as successful when the Code Engineer produces executable code and the Runner returns parseable estimates of β and P_f; the pipeline estimates are then compared against reference solutions. For most problems the reference is the Monte Carlo simulation result of a per-problem solver sweep with the validated backend solvers; for rare-event problems whose MCS reference does not reach the target coefficient of variation, the subset-simulation result is used instead. The framework completed all 20 problems, generating executable code and returning valid β and P_f in every case, with the reliability-index difference from the reference generally within Δβ ≤ 0.1. The one substantial discrepancy is p16 (bridge girder under correlated loads), where the pipeline returns β = 3.03 against a reference β = 2.00 — a method-selection failure on a strongly nonlinear limit state, not a code-execution failure; cases where an advanced method was selected for problems solvable more simply (p14, p18–p20) mainly cost extra computation without material accuracy loss. **Method-selection accuracy**: each benchmark problem is assigned a reference method category by the deterministic labeling criterion — rare-event problems with β > 3.5 go to Advanced regardless of nonlinearity; otherwise the label is FORM-based when the FORM estimate stays within 5% of the MCS reference reliability index, and MCS when it does not. The Planner alone is then run on each problem's ProblemSpec with the rest of the pipeline disabled, and its predicted category compared with the reference label; the metric is category accuracy, reported overall and per class. Three open-weight configurations receive the identical prompt: Gemma 4 E4B without fine-tuning (45% overall), Gemma 4 26B-A4B without fine-tuning (50%), and Gemma 4 E4B with Planner-only QLoRA (60%). The fine-tuned Planner recovers the minority classes — 4/8 FORM-based, 4/6 MCS, 4/6 Advanced — where both untuned models collapse onto the FORM-based column.

## Main Contribution

In the authors' framing, a multi-agent LLM framework that automates component-level structural reliability analysis end to end while preserving computational trustworthiness: language-based reasoning is separated from numerical computation so that β and P_f are computed only by deterministic execution of validated solvers, structured data contracts make every intermediate output traceable, and domain-specialized QLoRA fine-tuning of only the Method Planner is shown to improve a priori reliability-method selection more effectively than model scale alone.

## Key Design Ideas

- Five LLM agents plus one deterministic component: Orchestrator (intent routing), Problem Analyst (natural language → ProblemSpec), Method Planner (method-category selection, QLoRA fine-tuned), Code Engineer (spec + plan → solver code), Runner (non-LLM, executes code in an isolated subprocess and parses β and P_f), and Result Interpreter (numbers → engineering interpretation).
- Five typed data contracts fix every hand-off — ProblemSpec, AnalysisPlan, GeneratedCode, ExecutionResult, EngineeringInterpretation — so malformed fields, missing random variables or ill-formed limit-state functions are caught at the stage that produced them, and the final estimate is traceable back through method, code and execution.
- Numerical results are never generated by an LLM; the Code Engineer must emit code printing β and P_f on the final two lines in a fixed format so the Runner can parse deterministically.
- Method selection is a closed set of three categories — FORM-based (FORM, SORM, FORM-based importance sampling), MCS, and Advanced (subset simulation, cross-entropy importance sampling, sequential importance sampling, combination line sampling) — with the specific method within a category deferred to a later gate.
- Only the Planner is fine-tuned: QLoRA on a 4-bit-quantized frozen Gemma 4 E4B with a rank-16, α = 16 adapter, 4 epochs, learning rate 2 × 10⁻⁴, effective batch size 4, 8-bit AdamW and a linear schedule, trained on a single 24 GB RTX A5000 via Unsloth's FastModel loader with the vision tower frozen.
- The labeling criterion (β > 3.5 → Advanced; 5% FORM-vs-MCS agreement threshold otherwise) is presented as a replaceable design choice: changing it requires regenerating labels and retraining the Planner only, leaving the other agents untouched.
- Human-in-the-loop confirmation gates pause the workflow at four points, including category confirmation and, for the Advanced category, method choice; a FORM-based first pass can be refined once with SORM or FORM-based importance sampling.
- Open-weight models throughout, with local execution and no dependence on closed APIs.

## Strengths

- The held-out benchmark is deliberately built so no single method dominates — 11 distribution families, 2 to 30 random variables, linear through strongly nonlinear limit states, common through rare failure probabilities — rather than sampling easy cases.
- Reference solutions come from validated solvers with an explicit fallback (subset simulation) for rare-event problems where the MCS reference does not reach its target coefficient of variation, so the ground truth itself is defensible.
- The method-category labeling rule is published as an explicit deterministic criterion with stated thresholds, making the scoring reproducible and the labels auditable.
- The Planner evaluation isolates a single decision from the rest of the pipeline and holds the prompt identical across three configurations, so the fine-tuning effect is separated from model scale.
- Reporting confusion matrices rather than only overall accuracy exposes the failure mode that matters — untuned models defaulting to FORM-based, the unsafe direction of misselection for nonlinear and rare-event problems.
- The end-to-end results table publishes both pipeline and reference β and P_f for all 20 problems, and the paper analyses its own worst case (p16) rather than reporting only the aggregate.

## Limitations

- Restricted to component-level reliability with a single limit-state function; system-level reliability with multiple limit states is deferred, and no dedicated system-reliability algorithms are included.
- Limit-state functions must be evaluable directly inside the generated code — problems requiring external numerical models such as finite-element analysis are outside the present implementation, which the authors identify as the main barrier to realistic engineering cases.
- Standards information is not retrieved from authoritative documents: the user supplies the probabilistic model, and target reliability levels are handled at interpretation using preset reference values and model judgement.
- Method-category accuracy is 60% even for the best configuration, and the p16 case shows that a wrong category can propagate into a materially wrong reliability index (β = 3.03 against a reference of 2.00).
- Repository note: the benchmark is small (n = 20) and unnamed, and the three compared configurations are two sizes of one open-weight model family plus a fine-tuned variant of the smaller one, so the comparison is closer to an ablation of the authors' own design than to a cross-system leaderboard; per-class results rest on 6–8 problems each.
- Repository note: source code, fine-tuned model weights and benchmark problems are stated as "will be made publicly available on GitHub upon acceptance", so at the time of carding no artifact URL could be verified.
- Repository note: the paper reports no cost, latency or token accounting, so the computational-efficiency argument motivating method selection is not measured on the agent side.
