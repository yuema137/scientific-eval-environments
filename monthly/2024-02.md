# February 2024 Monthly Report

## Month at a Glance

- Two works entered the knowledge base this month, and both are new releases: [TravelPlanner](../works/travelplanner.md), first public on 2024-02-02, and [LoTa-Bench](../works/lota-bench.md), first public on 2024-02-13.
- They share one conclusion from opposite ends of the "planning" space: an agent's plan should be judged by running it, not by comparing it to a reference. Both make planner evaluation execution-grounded and fully automatic.
- That replaces two weaker signals. [TravelPlanner](../works/travelplanner.md) scores constraint satisfaction with deterministic scripts rather than surface similarity or an LLM judge; [LoTa-Bench](../works/lota-bench.md) executes plans in a simulator rather than relying on human plan inspection.
- Where an automated number exists, the gap it exposes is stark: on [TravelPlanner](../works/travelplanner.md), GPT-4 with ReAct reaches a 0.6% final pass rate even though it delivers a plan far more often.
- Neither work carries a canonical science or engineering domain — one lives in an embodied household simulator, the other in a closed travel sandbox — so there is no domain section this month.

## What Changed This Month

**Planner evaluation moves from comparison to execution, and the automated score exposes how far agents fall short.** The older path for judging language-model planners measured a plan against something else: a human reading the proposed plan, or a match to a reference plan. That path can confirm a plan looks right without confirming it works, and it is too manual to run at the scale needed to sweep models and prompts. February 2024 adds two benchmarks that both swap comparison for execution, approaching the same idea from very different substrates.

[TravelPlanner](../works/travelplanner.md) freezes a large multi-source database — 3,827,361 flight records plus city, distance, restaurant, attraction, and accommodation data — into a closed sandbox, then asks a language agent to search it, retain the relevant findings, and assemble a feasible three-, five-, or seven-day itinerary across 1,225 curated travel intents. Success is not similarity to a gold plan. Deterministic scripts check environment constraints such as unavailable transport, eight commonsense requirements, and explicit user constraints covering budget, rooms, cuisine, and transport, and the Final Pass metric requires every applicable check to hold at once. The automated score is what makes the shortfall legible: GPT-4 with ReAct reaches a 0.6% final pass rate even though it delivers a plan far more often, which locates the failure in constraint satisfaction rather than in producing output at all.

[LoTa-Bench](../works/lota-bench.md) closes the same inspection-to-execution loop for embodied task planning. The LLM proposes a skill sequence for a home-service instruction, the simulator runs it, and success is graded automatically against goal conditions — over two independent dataset-simulator stacks, ALFRED on AI2-THOR and an extended Watch-And-Help on VirtualHome. Two stacks guard the conclusion against any single simulator's idiosyncrasies, and automated goal checking makes model and prompt ablations cheap enough to run at scale, where prior practice was qualitative inspection.

Both results stop at the same boundary in two ways. First, on coverage: [TravelPlanner](../works/travelplanner.md)'s sandbox is static and travel-only, so it does not test open-world change or other planning domains, and its strict Final Pass needs the component metrics to separate retrieval, completion, and constraint failures; [LoTa-Bench](../works/lota-bench.md) is simulation-only with no physical robot, and its exact task and model counts await full-paper validation, since the card was compiled from the abstract and official repository. Second, on what is measured: both score whether the executed outcome met the goal, not whether each intermediate choice was the best one available — the distinction the topic sections below make explicit.

## Selected Topic Developments

### [Planning & Decision-Making Evaluation](../topics/planning_decision_evaluation.md)

Both works are explained here because planning is the sharper lens on each, and together they mark a specific move within this topic: the validity signal comes from running the plan rather than matching it. That choice has a cost the topic is careful about. Because the score is execution-grounded, neither benchmark isolates planning from execution — a sound plan can still fail when a tool returns nothing or the simulator trips, and both count that as a failure. So they answer "did this plan work," not "was this the best plan": in the topic's comparison, [TravelPlanner](../works/travelplanner.md) and [LoTa-Bench](../works/lota-bench.md) both sit on the not-isolated side and offer no counterfactual-alternative metric.

What each contributes within that constraint is a different grade of execution signal. [TravelPlanner](../works/travelplanner.md) reports component constraint pass rates — environment, commonsense, and hard — alongside full-plan feasibility, so a reader can see which constraint family broke rather than only that the plan failed; the environment also returns feedback when a search fails, so completion depends on adjusting to unavailable options, not just on a first-pass plan. [LoTa-Bench](../works/lota-bench.md) reports executed goal satisfaction over its two simulator stacks. This is the same reason both diverge from a tool-free, match-scored planner such as [NATURAL PLAN](../works/natural-plan.md), which supplies every fact in context and removes execution as a confound: the February works deliberately keep execution in the loop and pay for it with attribution ambiguity between a weak plan and a good plan that failed downstream.

### [General Long-Horizon Agent Benchmarks](../topics/long_horizon_evaluation.md)

Seen from the horizon axis, the same two works test something the planning lens does not: whether an agent can carry a task through many dependent steps whose earlier actions change later state. [TravelPlanner](../works/travelplanner.md) runs interactive trajectories capped at 30 steps, interleaving tool retrieval with environment feedback, so a failed search forces the agent to remember what it has found and revise — completion depends on sustaining that loop, not on a single response. [LoTa-Bench](../works/lota-bench.md) contributes multi-step skill-sequence plans executed to goal satisfaction, where each skill's effect conditions what the next skill can do. Neither adds a dense intermediate-progress metric; both are graded on the terminal goal, which is why the choice-quality reading of these works stays in [Planning & Decision-Making Evaluation](../topics/planning_decision_evaluation.md) above rather than being repeated here.
