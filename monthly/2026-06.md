# June 2026 Monthly Report

> **English** | [简体中文](../zh/monthly/2026-06.md)

> **Coverage:** First appearances during 2026-06

## Month at a Glance

June 2026 is the month where this repository's expanded scope starts to look structurally justified rather than aspirational. The raw count is large — 36 first appearances — but the more important change is that the new work no longer reads like a flat list of domain benchmarks. Three lines become visible at once: scientific benchmarks are moving closer to real workflows and executable artifacts; skill work is becoming a measurement layer in its own right rather than a loose intuition about "agent capability"; and process-level evaluation is being attached to concrete control points such as validators, rubrics, and planning steps.

The month is also unusually good at showing why final success is not enough. Structural analysis, industrial process control, scholarly information seeking, software engineering, and reusable skills all arrive with the same underlying claim: if the evaluator cannot say which step failed, which subskill was missing, or which validator blocked a bad action, the benchmark may rank systems but it does not yet guide improvement.

## What Changed This Month

### [Scientific Agent Benchmarks](../topics/scientific_agents.md)

The strongest scientific-benchmark pattern this month is a move away from "ask a domain-flavored question and grade the text answer" toward evaluating an agent against the artifact or workflow the field actually cares about. [Agentic Large Language Models for Automated Structural Analysis of 3D Frame Systems](../works/agentic-large-language-models-for-automated-struct.md) does not ask whether a model can talk about structures; it asks whether it can generate executable SAP2000 scripts whose monitored responses stay within 1% of a ground-truth model. [A Case Study of Evaluating AI Agents on a Neuroscience Data-to-Discovery Pipeline](../works/a-case-study-of-evaluating-ai-agents-on-a-neurosci.md) does the same thing for a fly-optogenetics pipeline, where the object of evaluation is a real research pipeline that scientists normally assemble by hand. [ALeRCE Text-to-SQL](../works/alerce-text-to-sql.md) narrows the surface further: a small benchmark, but one built around a database that astronomers actually query.

At the same time, several June works show that "realistic" does not just mean "more domain nouns." It means evaluation has to model the control boundary around the agent. [Autonomous Action Execution (AAE) Framework](../works/aae-framework.md) is useful here because it grades a system whose LLM is deliberately not allowed to act directly: every suggested action is filtered through deterministic validation over the plant topology. [PowerAgentBench-SS](../works/poweragentbench-ss.md), [PDAgent-Bench](../works/pdagent-bench.md), [GeoNatureAgent Benchmark](../works/geonatureagent-benchmark.md), [ScholarQuest](../works/scholarquest.md), [NatureBench](../works/naturebench.md), and [PhySciBench](../works/physcibench.md) all contribute to the same broader shift. They are not one coherent benchmark family, but together they make June look like a month where field-specific evaluation stopped being satisfied with static QA proxies.

There is also a second, quieter line running through the month: benchmark construction itself is being treated as a scientific object. [FrontierCode](../works/frontiercode.md) and [GeneBench-Pro](../works/genebench-pro.md) push on validity and contamination; [Curation-Bench](../works/curation-bench.md) turns the benchmark into part of a data-improvement loop; [SciAgentArena](../works/sciagentarena.md), [scBench-Long](../works/scbench-long.md), and [Agents' Last Exam](../works/agents-last-exam.md) widen the space of long-horizon or difficulty-calibrated evaluation. The practical takeaway is that June's scientific benchmark work is not only asking "what can the agent do?" but also "what kind of evaluator do we need if we want the answer to be actionable?"

### [Skill Hierarchy](../topics/skill_hierarchy.md)

June's skill work is much more concrete than a generic claim that agents "use skills." The main change is that skills are becoming measurable objects with their own evaluation surfaces. [A Framework for Evaluating Agentic Skills at Scale](../works/a-framework-for-evaluating-agentic-skills-at-scale.md) treats a skill repository as something that can be operationalized into executable tasks and scored at scale. [Skill Coverage](../works/skill-coverage.md) and [SkillJuror](../works/skilljuror.md) then ask two different but complementary questions: did the agent actually cover the intended behavior constraints, and does the way a skill is organized change how well it works?

Other June entries make hierarchy matter because they separate levels that used to collapse into one score. [ATOM-Bench](../works/atom-bench.md) splits atomic from compositional robotic competence, so a failure can be blamed on a missing primitive or on bad reuse rather than vaguely on "the policy." [PDAgent-Bench](../works/pdagent-bench.md) does something similar for VLSI physical design by placing conceptual and tool-grounded tasks alongside closed-loop workflow execution. [SCR-Bench](../works/scr-bench.md), [SkillAudit](../works/skillaudit.md), and [RubricsTree](../works/rubricstree.md) reinforce the same point from different angles: if you want to improve reusable agent behavior, you need an evaluator that can say which layer of the skill stack broke.

[Agent Skill Evaluation and Evolution: Frameworks and Benchmarks](../works/agent-skill-evaluation-survey.md) matters here not because it is a survey, but because it makes the month's scattered skill papers legible as a field. By the end of June, "skill hierarchy" no longer looks like an incidental annotation category; it looks like a stable evaluation problem with its own methodologies.

### [Trajectory Evaluation](../topics/trajectory_evaluation.md)

If June has one clean conceptual center, it is that the trajectory is no longer being treated as debugging residue. It is becoming the primary evidence object. [AISE-Bench](../works/aise-bench.md) pairs answers with full API trajectories and validated parameters; [RigorBench](../works/rigorbench.md) scores engineering process discipline from the execution trace; [TELBench](../works/telbench.md) and [QVal](../works/qval.md) contribute additional step-sensitive evaluation surfaces; [AAE Framework](../works/aae-framework.md) makes the accepted-versus-rejected action proposal itself part of the measured behavior.

This matters because the month repeatedly shows the same failure of outcome-only evaluation. A system can finish the task, yet do it with brittle planning, unsafe action suggestions, weak skill use, or sloppy engineering process. Conversely, a system can fail late after making several good decisions that a binary score would throw away. June's trajectory work is important less for any one benchmark than for the aggregate methodological claim: if the evaluator cannot see the intermediate state, the selected tool call, the validator intervention, or the skill constraint that was missed, then it is not yet an evaluator you can use to drive development.

## Selected Topic Developments

June is the first month in this archive where [Scientific Agent Benchmarks](../topics/scientific_agents.md), [Skill Hierarchy](../topics/skill_hierarchy.md), and [Trajectory Evaluation](../topics/trajectory_evaluation.md) feel tightly coupled rather than merely co-occurring. The same papers keep crossing those boundaries because the repository's broader thesis is becoming empirically visible: better evaluation is not just about measuring agents at the end, but about exposing the specific structure that lets you decide what to improve next.
