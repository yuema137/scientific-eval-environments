## Month at a Glance

- One work entered the knowledge base this month, and it is a new release: [AgentBoard](../works/agentboard.md), first public on 2024-01-24.
- Its single argument is narrow but load-bearing: a binary success rate hides how a multi-turn agent actually fails, so evaluation should record intermediate progress, not just the final outcome.
- The mechanism is subgoal annotation. Every task carries a chain of subgoals, and the primary metric is the fraction completed — a trajectory that fails at the end still earns a score for the progress it made.
- The cost is explicit and bounded: subgoals are authored by hand, so coverage grows only as fast as human decomposition allows.

## What Changed This Month

**Agent evaluation gains a partial-credit signal for multi-turn tasks.** The prevailing evaluation path scores an agent by whether it reaches the final goal. On a long, partially observable task that terminal label is coarse: an agent that completes four of five dependent steps before a fatal error and an agent that never starts the right task both register as a single failure. [AgentBoard](../works/agentboard.md) changes the measured quantity. It annotates each task with an ordered chain of subgoals and reports a *progress rate* — the fraction of those subgoals completed within a trajectory — while retaining binary success rate as a coarse baseline for comparability with prior benchmarks. The evidence is a unified suite of 1,013 environments spanning nine task types across four families (embodied, game, web, and tool-use agents), all treated as multi-turn and partially observable, paired with an analytical dashboard that slices results by task family and capability dimension rather than only ranking systems.

The result stops where the annotation stops. Progress rate is only as good as the subgoal chains a human authored, and extending the benchmark to a new task family requires that decomposition to be done by hand. Progress rate is offered as a complement to success, not a replacement, so the older terminal signal remains in the report rather than being discarded.

## Selected Topic Developments

### [Trajectory Evaluation](../topics/trajectory_evaluation.md)

AgentBoard is the primary reference here because it keeps the route between prompt and result instead of collapsing it to one label. Within this topic it defines the **subgoal-based** design line: trajectories are annotated with a chain of subgoals, and the headline metric is the fraction completed. That choice is what lets the evaluator separate "made significant progress" from "failed entirely," which a binary outcome cannot express, and the dashboard turns the retained trace into a diagnostic artifact rather than a leaderboard row. The same subgoal-progress mechanism is what places the work on two adjacent axes:

- On [Skill Hierarchy](../topics/skill_hierarchy.md), the per-task subgoal chain acts as a per-subgoal capability signal — decomposition applied to each task individually, rather than to a capability shared across tasks.
- On [Credit Assignment](../topics/credit_assignment.md), assigning credit per completed subgoal is one concrete answer to *where* along a trajectory reward should land, as opposed to per graded subtask or per trajectory-level dimension.
